# ADR-0004: 広告（収益化）導入方針

## Status

Proposed

> 本 ADR は方針の合意形成を目的とする。実装は将来の別 Issue とし、現時点では Accepted（実装着手）ではなく Proposed とする。

## Context

Issue #15 で、一般公開後の収益化手段として「邪魔にならない形式の広告」導入が検討依頼された。方針は以下。

- 強制ポップアップ・強制動画視聴は NG（UX を損なわない）
- 広告サービス（Google AdSense 等）・配置は要検討
- **一定のアクセス数が見込める段階で導入**（＝現時点では時期尚早）

一方、`docs/PRD.md` では「収益化機能」は明示的に**スコープ外（OUT）**と定義されている。本 ADR はこの方針を見直す位置づけであり、収益化を将来スコープへ昇格させる際の意思決定記録となる。

### 検討した選択肢

各広告／収益化手段を、UX 親和性・プライバシー負荷・審査ハードル・収益性・TuneCard との親和性で比較した。

| 選択肢 | UX 親和性 | プライバシー負荷 | 審査 | 収益性 | TuneCard との親和性 |
|--------|-----------|------------------|------|--------|---------------------|
| 1. Google AdSense | 中（バナーで枠を取る） | 高（行動ターゲティング・CMP 必須） | 厳しい（薄いユーティリティは却下リスク大） | 高 | 低（コンテンツ量が乏しい） |
| 2. Carbon Ads | 高（上質な1枠・静的） | 低（トラッキング少） | あり（媒体審査・トラフィック要件） | 中 | 中（開発者向け媒体寄りで音楽層とはずれる） |
| 3. 音楽系アフィリエイト（Spotify/Amazon Music 等） | 高（コンテンツに溶け込む） | 低（クッキー最小・行動追跡なし） | 緩い | 中（単価・送客次第） | 高（楽曲シェアと文脈が一致） |
| 4. 寄付モデル（GitHub Sponsors / Buy Me a Coffee） | 最高（広告枠ゼロ） | 最低 | なし | 低・不安定 | 中 |
| 5. 自前ハウス広告／相互リンク | 高 | なし | なし | なし（収益化前提ではない） | 高（枠検証のプレースホルダーに有用） |

補足:

1. **Google AdSense** — 最も一般的で収益性は高いが、TuneCard は「URL 貼付 → シェア文生成」の単機能ユーティリティでコンテンツが薄く、AdSense の「価値の低いコンテンツ」ポリシーで審査落ちするリスクが高い。導入にはプライバシーポリシー・同意管理（CMP）が必須で、PWA の Service Worker キャッシュ調整（後述）も必要。
2. **Carbon Ads** — プライバシー配慮型で UX 親和性は高いが、開発者・デザイナー向け媒体が中心で、TuneCard の音楽シェア層とのマッチは限定的。媒体審査・トラフィック要件もある。
3. **音楽系アフィリエイト** — コンテンツとの親和性が最も高く UX を損ねにくい。審査が比較的緩く、行動追跡を伴わないためプライバシー負荷も小さい。収益は単価・送客数に依存。
4. **寄付モデル** — UX 影響ゼロ・プライバシー配慮最大だが、収益は不安定。
5. **自前ハウス広告** — 収益化前に「広告枠の見え方・UX 影響」を検証するプレースホルダーとして有用。

## Decision

### 当面は広告を導入しない（現状維持）

理由:

- **(a) 導入条件未達** — Issue #15 自身が「一定のアクセス数が見込める段階で導入」としており、現状はその段階に至っていない。
- **(b) AdSense 審査リスク** — 薄いユーティリティのため審査通過が不確実で、導入コストに見合わない。
- **(c) プライバシー基盤未整備** — プライバシーポリシーページ・同意管理（CMP）が未整備で、行動ターゲティング広告の前提を満たさない。

### 将来導入する場合の第一候補は「音楽系アフィリエイト」

UX・プライバシー・コンテンツ親和性のバランスが最良のため。AdSense は、審査・CMP・Service Worker 対応のコストに見合うアクセス数が確認できた段階で再評価する。

### 実装方針（着手は別 Issue）

導入時は **ADR-0002（Provider 抽象化パターン）** に倣い、特定の広告サービスに依存しない設計とする。

- `TrackInfoProvider` と同様に、広告枠を抽象化した `AdSlot` コンポーネント（または広告 Provider 抽象）を用意し、AdSense・アフィリエイト等を差し替え可能にする。
- feature flag（`VITE_ADS_ENABLED` 等）で制御し、**デフォルト無効**とする。`src/hooks/useTrackInfo.ts` の `import.meta.env.VITE_WORKER_URL` による分岐と同じ要領で、環境変数未設定時は広告を一切読み込まない。

## Consequences

### 導入の前提条件（満たすまで導入しない）

- アクセス数 KPI の達成（例: 月間 PV／アクティブユーザー数の目安を別途設定）。
- プライバシーポリシーページの整備。
- 行動ターゲティング広告を使う場合は同意管理（CMP）の導入（GDPR/CCPA 対応）。

### 将来 Issue 用の技術 TODO

- **CSP**: `public/_headers`（未作成）で Content-Security-Policy を定義し、`script-src` に広告配信ドメインを許可する。
- **PWA キャッシュ**: `vite.config.ts` の workbox 設定で広告スクリプトを precache から除外する。現状 `globPatterns: ['**/*.{js,...}']` が `.js` を precache 対象にしているため、`globIgnores` での除外、または外部広告ドメインを `runtimeCaching`（networkFirst）に設定し、オフライン時は表示をスキップする。
- **配置案**: `src/App.tsx` の `<main>`（`max-w-md` レイアウト内、`pb-8` 領域）下部に1枠のみ。強制表示・ポップアップは行わない。
- **耐障害性**: 広告は非同期読込とし、ロード失敗時もアプリ本来の UX に影響しないようにする。
